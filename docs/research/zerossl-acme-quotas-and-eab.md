# ZeroSSL ACME quotas and EAB at scale

_As of 2026-09-23. Primary sources only. This report distinguishes provider documentation, user reports, and an endpoint observation._

## Documented limits

| Topic | Finding |
| --- | --- |
| Certificate volume | ZeroSSL advertises unlimited free 90-day ACME certificates. Its comparison table lists no Let’s Encrypt-style caps for certificates per registered domain, new orders per account per three hours, or account registrations per IP per three hours. These statements do **not** establish that every anti-abuse threshold is absent: ZeroSSL says abusive clients may be limited or blocked. [ACME documentation](https://zerossl.com/documentation/acme), [ZeroSSL limits comparison](https://help.zerossl.com/hc/en-us/articles/17864245480093-Advantages-over-Using-Let-s-Encrypt) |
| Request rate | The same comparison specifies **7 overall ACME requests per second**. It does not say whether that rate applies per account, source IP, or another scope. Its [“No Rate Limits” feature-page label](https://zerossl.com/features/acme) therefore cannot be used as an operational throughput guarantee. The table also does not establish whether the separate email EAB API endpoint shares this limit. [ZeroSSL limits comparison](https://help.zerossl.com/hc/en-us/articles/17864245480093-Advantages-over-Using-Let-s-Encrypt) |
| EAB generation | EAB is required. ZeroSSL says credentials have been reusable since March 2022, but limits **new EAB credentials per user per day** without publishing the number. Its documented API method requires an `access_key`; the email-only method is absent from that documentation. [ACME documentation](https://zerossl.com/documentation/acme), [EAB API documentation](https://zerossl.com/documentation/acme/generate-eab-credentials) |
| Dashboard access | ZeroSSL says viewing more than 100 ACME certificates through its dashboard or REST API requires Basic, and more than 100,000 requires Premium. This is a management-access condition, distinct from the advertised free ACME issuance. [List Certificates documentation](https://zerossl.com/documentation/api/list-certificates) |

For comparison, Let’s Encrypt’s **50 new certificates per registered domain per seven days** is global across accounts; an override can be requested. Its ARI-coordinated renewals are exempt from rate limits, while new managed hostnames consume the registered-domain allowance. Changing ACME accounts does not remove that shared-domain limit. [Let’s Encrypt rate limits](https://letsencrypt.org/docs/rate-limits/)

## Email-only EAB and account topology

**Observed, with limited scope:** Caddy’s current ACME integration posts form-encoded `email` to `https://api.zerossl.com/acme/eab-credentials-email` before registering a ZeroSSL account. Caddy adds that email as the ACME account contact and checks the JSON error field because the API can return errors with HTTP 200. This code is in **Caddy**, while CertMagic supplies the ordered-issuer retry loop; CertMagic’s ZeroSSL ACME documentation describes providing EAB via the API or dashboard. [Caddy EAB implementation](https://github.com/caddyserver/caddy/blob/c18099a0af5e88c8d9da0b9d797f6f2c62d60a23/modules/caddytls/acmeissuer.go#L306-L421), [CertMagic issuer loop](https://github.com/caddyserver/certmagic/blob/722bda8d9d6b48f16452de4d907a2cfc726affa9/config.go#L693-L746), [CertMagic ZeroSSL documentation](https://github.com/caddyserver/certmagic#zerossl)

On 2026-09-23, one POST with the deliberately invalid value `email=not-an-email` returned HTTP 200 and `{"success":false,"error":{"code":2901,"type":"invalid_email","info":null}}`. This establishes that the [email endpoint](https://api.zerossl.com/acme/eab-credentials-email) still routes and validates input. It does **not** verify successful issuance for a real address, an account-creation workflow, or an endpoint-specific quota. No real address was submitted.

The [current daemon](https://github.com/getployz/ployz2/blob/6c21d8b1f97ac8175eba02bb9d1b4eb901571f34/core/crates/ployzd/src/certificates.rs#L696-L722) stores one `account.json` per Machine and replaces it when the directory changes. It also [starts all due hostname orders concurrently](https://github.com/getployz/ployz2/blob/6c21d8b1f97ac8175eba02bb9d1b4eb901571f34/core/crates/ployzd/src/certificates.rs#L473-L504). Fetching a fresh email EAB for each Machine could hit ZeroSSL’s unpublished per-user/day generation limit; reusing one EAB would avoid repeated generation but require distributing that credential. A shared ACME account would reduce registrations but require distributing and protecting its private key. ZeroSSL publishes no account-order cap that makes a shared account necessary for quota avoidance; neither topology addresses a possible source-IP request limit. [ZeroSSL ACME documentation](https://zerossl.com/documentation/acme), [ZeroSSL limits comparison](https://help.zerossl.com/hc/en-us/articles/17864245480093-Advantages-over-Using-Let-s-Encrypt)

## Reliability evidence and contractual uncertainty

**Observed reports, not an availability measurement:** A Caddy user reported that Let’s Encrypt failure fell back to ZeroSSL within seconds for static sites, but not for routes added through Caddy’s API. Another reported ZeroSSL finalization timeouts and an HTTP 504 during a high-volume issuance burst; Let’s Encrypt also timed out in that incident, so it does not isolate a ZeroSSL outage. A cert-manager user supplied logs of ZeroSSL ACME HTTP 429 responses during multi-domain issuance and reported ZeroSSL support’s advice to throttle or retry. These cases justify handling 429 responses and retries, but cannot establish ZeroSSL’s fleet-wide reliability or that Ployz needs preemptive pacing. [Caddy fallback report](https://github.com/caddyserver/caddy/issues/7084), [Caddy high-volume report](https://github.com/caddyserver/caddy/issues/4262), [cert-manager 429 report](https://github.com/cert-manager/cert-manager/issues/5867)

**Contract scope:** The [Ployz daemon runs on the user's Machine](https://github.com/getployz/ployz2/issues/976#issuecomment-5792410895). If it registers that user's ZeroSSL account using their email, shipping a client with a ZeroSSL fallback does not itself make Ployz the certificate subscriber or a reseller of ZeroSSL. ZeroSSL's posted Terms restrict commercial third-party service use without written consent, while its live [ACME directory](https://acme.zerossl.com/v2/DV90) names the separate [Sectigo Certificate Subscriber Agreement](https://www.sectigo.com/uploads/legal/Certificate-Subscriber-Agreement-3.0-click.pdf), which recognizes a hosting company submitting a request on a subscriber's behalf. The terms question becomes material if Ployz later operates one shared ZeroSSL account or issues certificates as a hosted service; clarify that model with [ZeroSSL](https://help.zerossl.com/hc/en-us/requests/new) before adopting it. This is a scope inference, not a legal determination. [ZeroSSL Terms](https://zerossl.com/legal/terms)

## Google Trust Services

Google Public CA obtains EAB through an authenticated **Google Cloud project**, IAM role, and Public CA API or CLI. Email is not the EAB acquisition credential; Google’s example nevertheless supplies an email when registering the ACME account. Each EAB secret must be used within seven days and registers exactly one ACME account. There is no documented email-only bootstrap comparable to Caddy’s ZeroSSL call. [Google Public CA tutorial](https://docs.cloud.google.com/certificate-manager/docs/public-ca-tutorial), [EAB API method](https://docs.cloud.google.com/certificate-manager/docs/reference/public-ca/rest/v1/projects.locations.externalAccountKeys/create)

Google documents quotas shared by all ACME accounts in one project: **100 `newOrder` requests/hour**, **300 new authorizations/hour**, and **25 `newAccount` requests/minute, 100/hour**. It instructs clients to honor HTTP 429 `Retry-After`; the published table does not list a registered-domain weekly cap. Public CA certificate requests are free. Multiple per-Machine accounts do not multiply project quota, and each would need its own single-use EAB. GTS is therefore a credible **provisioned** fallback for Ployz-managed clusters, but not a zero-configuration universal daemon fallback. [Google quotas](https://docs.cloud.google.com/certificate-manager/docs/quotas), [Google Public CA tutorial](https://docs.cloud.google.com/certificate-manager/docs/public-ca-tutorial)

## Recommended issuer order and daemon Certificate Policy knobs

1. **Daemon default:** **Let’s Encrypt → ZeroSSL** when the operator supplies their own contact email for ZeroSSL account registration. Without an email or configured EAB, use Let’s Encrypt alone and report why ZeroSSL was unavailable. This preserves the [Hosted DNS decision](https://github.com/getployz/ployz2/issues/976#issuecomment-5792410895) without assuming Ployz owns the CA account. Pursue Let’s Encrypt’s documented registered-domain override as a separate capacity lever for Ployz-managed names. [Let’s Encrypt rate limits](https://letsencrypt.org/docs/rate-limits/)
2. **Other issuer:** Keep **Google Public CA** as a provisioned option, not the built-in second fallback: it needs a Google Cloud project and a fresh EAB key for each Machine's account. If Ployz ever issues certificates from a shared account or service, settle that account's terms and provisioning separately. [Google tutorial](https://docs.cloud.google.com/certificate-manager/docs/public-ca-tutorial), [Google quotas](https://docs.cloud.google.com/certificate-manager/docs/quotas), [ZeroSSL Terms](https://zerossl.com/legal/terms)
3. **Policy surface:** Replace the single `directory_url` with an **ordered issuer list**. Each issuer needs its directory and EAB credentials or a contact email for ZeroSSL's bootstrap. Keep the existing renewal, backoff, key-type, and probe settings shared. Persist ACME accounts **per directory per Machine** so switching issuers cannot overwrite one account with another. Add no rate-limit policy knob based on the seven requests/second figure: its scope is unpublished and this research does not show a problem for Ployz's one-name orders. Honor `Retry-After` on 429 responses when supplied; add simple pacing only if bursts actually cause 429s. [Current policy](https://github.com/getployz/ployz2/blob/6c21d8b1f97ac8175eba02bb9d1b4eb901571f34/core/crates/ployz-core/src/domain/certificate_policy.rs#L78-L116), [current account storage](https://github.com/getployz/ployz2/blob/6c21d8b1f97ac8175eba02bb9d1b4eb901571f34/core/crates/ployzd/src/certificates.rs#L696-L722), [ZeroSSL limits comparison](https://help.zerossl.com/hc/en-us/articles/17864245480093-Advantages-over-Using-Let-s-Encrypt)
