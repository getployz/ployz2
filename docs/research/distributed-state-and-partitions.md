# Distributed state and partition semantics

Status: frozen-baseline research for `getployz/ployz2#4`

Reference implementation: `psviderski/uncloud` at [`b7e224a1eff98813b1d1a32034d977be24be994e`](https://github.com/psviderski/uncloud/tree/b7e224a1eff98813b1d1a32034d977be24be994e)

## Executive conclusion

Uncloud is an available, quorum-free collection of machine-local control loops. It is not one logically serial control plane. Each daemon writes to its local Corrosion database. Corrosion replicates those writes through gossip and CRDT-backed SQLite tables. Administrative commands enter through one reachable machine, then run there or get proxied directly to selected machines. DNS and Caddy are asynchronous projections of replicated container observations. Docker remains the authority for whether a container actually exists and runs on a given machine. This matches the stated preference for no control plane, imperative operations, and eventual state sync. ([README](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/README.md#L19-L21), [design](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/misc/design.md#L101-L122), [store](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/store.go#L25-L60))

The weak semantics are part of the architecture to reproduce. A reachable partition can keep accepting local writes and direct operations. There is no global uniqueness fence, allocation reservation, atomic multi-machine operation, or post-partition intent reconciler. A healed cluster converges at the storage layer, but convergence can preserve a domain contradiction such as two machine records with the same name or subnet, or two service IDs with the same service name. The original design explicitly admits that CRDT convergence may not produce the state users intended. ([design](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/misc/design.md#L65-L74), [schema](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/schema.sql#L10-L42))

The Rust reconstruction should model these distinctions more precisely without strengthening them. In particular, types should distinguish a replicated observation from a live response, a complete broadcast from a partial one, and a locally judged member from a globally authoritative fact. They must not imply that Uncloud has consensus, fencing, durable reservations, transactions across machines, automatic relocation, or a desired-state reconciler.

## The actual model

([Uncloud store](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/store.go#L25-L60), [pinned Corrosion README](https://github.com/unlabs-dev/corrosion/blob/73c06daa55b840fc97e886822ae7fcd94dfdc539/README.md#L4-L45)) | Local write acceptance is synchronous. The entry daemon proxies remote gRPC calls. | Partition behavior | Each side can serve local reads, accept local writes, and operate on machines it can resolve and reach. Cross-partition calls fail or appear as partial broadcast results. Replication catches up after connectivity returns. ([design](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/misc/design.md#L55-L74), [broadcast error handling](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/api/proxy/backend.go#L115-L151)) | Availability is partition-local. There is no global admission rule that blocks a minority side. |

There is no lock, lease, reservation, or revalidation transaction. |
| Failure recovery | Docker restarts containers locally. Uncloud does not move them to another machine. Some operations contain narrow local compensation, but there is no cluster-wide rollback. ([design](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/misc/design.md#L116-L122), [replacement compensation](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/deploy/operation/container.go#L173-L258)) | Failed workflows can leave durable partial effects. |

## Replication and readiness

The replicated schema contains cluster key-value data, machine records, and container records. Primary keys protect only the row identities `key`, machine `id`, and container `id`. Machine names, service IDs, and service names have ordinary indexes, not uniqueness constraints. Services do not have their own authoritative replicated table. Their ID and name are derived from labels in container JSON. Each machine separately persists the complete service specification for each local container in a machine-local SQLite table. It combines that specification with live Docker inspection to build a `ServiceContainer`, then removes environment values before putting that observation into the replicated store. ([replicated schema](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/schema.sql#L1-L42), [local schema](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/db.go#L36-L43), [spec persistence](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/docker/server.go#L743-L758), [inspection](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/docker/service.go#L110-L141), [redaction](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/container.go#L88-L103))

Corrosion can expose a row before all of its columns arrive. Uncloud handles that state by omitting rows with empty JSON from machine and container listings. This means even one local read can be structurally incomplete without returning an error for the omitted item. The implementation treats that as expected replication behavior. ([machine omission](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/store.go#L180-L223), [container omission](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/container.go#L139-L177))

Joining has one deliberate catch-up barrier. The existing member captures its per-actor maximum versions and passes that map to the joiner. The joining daemon waits until its local store reaches those maxima, then waits until its own Corrosion replica reports no currently known gaps, before it starts components that depend on cluster state. The wait can continue indefinitely and logs after five minutes. It reaches the captured version frontier with no locally known gaps. It does not prove global completeness, provide an ongoing freshness guarantee, or serialize allocations made while joining. ([captured version](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/cli/cli.go#L460-L489), [version and local gaps](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/store.go#L63-L117), [join watermark](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster.go#L369-L483))

Machine data and container data have different local authorities. A machine keeps its own identity and network configuration in local state. It checks that record at startup, on triggers, and every minute, then republishes only when the replicated row is missing or changed. Local Docker plus the machine-local service-spec database are authoritative for complete local service containers. A controller watches Docker events and also rescans every 30 seconds, then upserts redacted current observations and deletes missing records from the replicated store. ([machine republishing](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster.go#L485-L563), [local service inspection](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/docker/service.go#L110-L141), [Docker controller](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/docker/controller.go#L18-L24), [Docker synchronization](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/docker/controller.go#L150-L194))

This creates a useful hierarchy for the reconstruction:

1. Local daemon state is authoritative for that machine's own identity and network configuration.
2. Local Docker is authoritative for runtime containers on that machine.
3. The machine-local SQLite database is authoritative for the complete service specification attached to each local container.
4. The local Corrosion replica is a redacted, replicated observation of all machines and containers.
5. Membership is a local liveness judgment layered onto replicated machine records.
6. DNS and Caddy are projections of the replicated container observation.

These are not interchangeable sources of truth.

## Routing and observable cluster views

The CLI stores multiple entry connections and tries them in order until one succeeds. After it chooses an entry, that daemon supplies the machine map and forwards targeted calls. A request without proxy metadata executes on the entry daemon. One-to-one metadata selects a target. One-to-many metadata selects names, IDs, or `*` from the entry daemon's local replicated machine list. ([CLI](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/cli/cli.go#L94-L167), [client metadata](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/client.go#L78-L98), [proxy mapper](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/api/proxy/mapper.go#L41-L107))

The entry's view therefore determines both naming and fan-out. The mapper puts both IDs and names into one lookup namespace. A duplicate name, or a name equal to some machine ID, silently overwrites one entry according to iteration order. If a newly added machine has not replicated to the entry, `*` does not include it. If a stale machine remains in the entry's store, it can be selected and then fail during connection. The remote proxy reconnects in the background, but an unavailable target still makes the present call unavailable. ([mapper](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/api/proxy/mapper.go#L41-L107), [remote connection](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/api/proxy/remote.go#L70-L96))

Machine liveness is also entry-relative. `ListMachines` combines locally stored machine rows with Corrosion membership states seen by the responding daemon. Missing, dead, or unknown peers become `DOWN`. `SUSPECT` remains available to the client, and the responder always marks itself `UP`. ([membership synthesis](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster/cluster.go#L198-L241), [available filter](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/machine.go#L33-L74))

Most service inspection deliberately avoids treating replicated container rows as live truth. It broadcasts Docker queries to machines judged `UP` or `SUSPECT`, collects successful replies, and reports unreachable or failed machines as warnings with an incomplete result. A separate `InspectServiceFromStore` method explicitly documents that its result can be stale. Volume listing follows the same partial broadcast shape. ([service inspection](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/service.go#L88-L210), [service listing](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/service.go#L321-L385), [volume listing](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/volume.go#L51-L100))

The practical partition contract follows from those choices. A user can administer the machines visible and reachable from the chosen entry side. A command cannot operate through the partition boundary. Different sides can return different machine sets, different availability labels, and different service observations at the same time. One-to-many calls may succeed on some targets and return per-machine errors for others. This is an intended partial result, not a transaction failure. ([broadcast backend](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/api/proxy/backend.go#L115-L151), [service partial warnings](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/service.go#L127-L131))

## Conflict, uniqueness, and allocation

### Machine identity and subnet allocation

`AddMachine` reads the local replica, rejects a duplicate name, management IP, or WireGuard key in that snapshot, and builds an in-memory allocator from the observed subnets. The allocator scans for the first free `/24`. It does not reserve that choice anywhere before the new machine row is written. The source leaves a direct TODO to announce the addition, achieve consensus, and perhaps reject an addition from a minority partition. That machinery is intentionally absent in the frozen baseline. ([add machine](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster/cluster.go#L76-L183), [IPAM](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster/ipam.go#L11-L81))

Two concurrent additions can therefore both pass the checks and choose the same subnet from stale snapshots. They still get distinct random machine IDs, so the machine primary key does not conflict. After healing, both rows can coexist. The schema does not enforce unique names or subnets. The converged store can consequently contain duplicate names, duplicate management addresses, duplicate public keys, or overlapping machine subnets. This is a domain contradiction retained by storage convergence. ([machine schema](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/schema.sql#L10-L21), [allocation checks](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster/cluster.go#L109-L180))

The advertised cluster-unique container IP property depends on machine subnets being unique. Docker allocates container addresses inside each machine's bridge subnet. If a partitioned addition duplicates a machine subnet, Uncloud has no later allocator or reconciler that chooses a winner. The route and address contradiction survives until a user intervenes. ([README allocation description](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/README.md#L236-L248), [container address claim](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/README.md#L263-L269))

Machine rename has the same shape. The target machine updates its own local source state after checking its local store for a duplicate. That machine later republishes the record. Concurrent renames can choose the same name because there is no global fence and no unique schema constraint. ([rename](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/machine.go#L1107-L1180), [republishing](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster.go#L485-L563))

### Service identity

Service creation performs an optimistic name lookup before deployment. A new deployment generates a random service ID, while service name and ID are stored on each container as labels. Concurrent creators can both observe that a name is absent, produce different service IDs, and create containers with the same name. The client explicitly detects this state during inspection and requires an ID to disambiguate. A daemon TODO also calls out multiple same-name service IDs caused by concurrent creations. ([optimistic check](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/service.go#L21-L37), [ID generation](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/deploy/strategy.go#L505-L523), [duplicate detection](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/service.go#L152-L167), [daemon TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/machine.go#L1346-L1348))

Concurrent changes to the same CRR row are different from these domain duplicates. Corrosion's replicated change representation identifies the table, primary key, column, value, column version, database version, and actor. The conflict unit is therefore a cell, while changes to different columns remain distinct inputs. Corrosion delegates application and convergent winner selection to its embedded CR-SQLite binary. The exact competing-cell tie-break contract of that pinned binary is not reconstructible from Uncloud source, and Uncloud does not interpret which writer should win. Reconstruction should preserve the pinned dependency's semantics instead of inventing a domain-level winner. Separate IDs do not conflict at the CRDT layer at all, even when they violate a human uniqueness expectation. ([Corrosion README](https://github.com/unlabs-dev/corrosion/blob/73c06daa55b840fc97e886822ae7fcd94dfdc539/README.md#L17-L30), [CRR schema conversion](https://github.com/unlabs-dev/corrosion/blob/73c06daa55b840fc97e886822ae7fcd94dfdc539/crates/corro-types/src/schema.rs#L379-L380), [change application](https://github.com/unlabs-dev/corrosion/blob/73c06daa55b840fc97e886822ae7fcd94dfdc539/crates/corro-agent/src/agent/util.rs#L803-L858))

## Stale projections and a documented contradiction

DNS and Caddy subscribe to replicated container rows. They filter for containers whose last recorded state looks healthy. Neither component filters containers by the current Corrosion membership state of the hosting machine. Both files retain TODOs for that missing check. ([DNS resolver](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/dns/resolver.go#L38-L121), [Caddy controller](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/caddyconfig/controller.go#L80-L146))

When a remote machine crashes or becomes partitioned, its last healthy container rows can remain in the local replica. The surviving side can keep publishing those unreachable addresses through DNS and Caddy. Caddy has passive upstream failure handling, which can reduce repeated routing to failed backends, but the configuration source itself remains stale. ([container staleness warning](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/container.go#L18-L25), [Caddy passive health configuration](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/caddyconfig/caddyfile.go#L34-L39))

This behavior contradicts the design document's statement that DNS should adjust to only the containers available inside the current partition, followed by the proxy doing the same. The TODOs show that the gap was known. For reconstruction, the frozen implementation and its TODO are the contract. Do not silently upgrade the promise while rebuilding. ([design claim](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/misc/design.md#L148-L157), [DNS TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/dns/resolver.go#L38-L68), [Caddy TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/caddyconfig/controller.go#L132-L146))

The `sync_status` field does not close the gap. The store notes that a record marked `synced` can be outdated after a crash or partition, and subscription code has a TODO questioning whether the field is needed at all. It records successful local Docker synchronization, not cluster-wide freshness or reachability. ([status definition](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/container.go#L18-L25), [status TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/store/container.go#L208-L218))

## Partial-operation semantics

Deployments are plans of imperative operations executed in sequence. Execution stops on the first error. There is no outer transaction and no general rollback of prior operations. A simple run creates a container, starts it, and waits for health. Start or health failure can leave the newly created container behind. Replacement has one narrow compensation path for a health failure. It stops the new container, optionally restarts the old one, and intentionally retains the stopped new container for inspection. ([sequence](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/deploy/operation/sequence.go#L9-L20), [run](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/deploy/operation/container.go#L39-L67), [replace](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/deploy/operation/container.go#L173-L258))

The start-first update path acknowledges another weak edge. Caddy learns the new upstream asynchronously from replicated state, but the old container can be stopped before Caddy observes the new one. A TODO accepts that a one-replica service may have brief downtime. ([replacement TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/deploy/operation/container.go#L240-L246))

Service actions such as start, stop, and remove execute against the containers discovered at command time. Per-container operations run concurrently, then their errors are joined. Some containers may change successfully before another fails. Creating a service can also create named volumes before the deployment plan runs, so a later failure can leave those volumes in place. ([service creation](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/service.go#L39-L79), [service actions](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/service.go#L213-L319))

Machine lifecycle is also multi-step and optimistic. Add provisioning registers the new machine row before the new daemon has joined, caught up, and become a saved CLI entry point. A later failure can leave a registered but incomplete machine. Removal deletes containers first, triggers an asynchronous reset if possible, then deletes the machine row. It can proceed without reset when the target is unreachable. Cleanup of stored container records is best effort. ([add workflow](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/cli/cli.go#L330-L523), [remove workflow](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/cmd/uc/machine/rm.go#L98-L188), [store removal](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster/cluster.go#L244-L269))

An unreset or partitioned removed machine still regards its local machine state as authoritative. Its periodic sync recreates its missing row if necessary. After reconnection, that behavior can resurrect a removed machine record. The removal code tries to start reset first specifically to reduce this race, but comments that reset is asynchronous and optimistic. ([periodic publisher](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster.go#L485-L563), [optimistic reset](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/cmd/uc/machine/rm.go#L153-L166))

No background component turns these partial results back into a declared desired state. Docker only restarts containers on their original machine. User commands perform scheduling. Containers are not automatically moved when a machine fails. This is an explicit simplification, not a missing generic orchestrator layer. ([design](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/misc/design.md#L101-L122))

## Reconstruction constraints

The following is the smallest faithful contract for the Rust implementation.

1. Keep Corrosion as the distributed state engine and preserve its local-write, eventual-convergence behavior. Do not reimplement its conflict algorithm in Rust. The frozen Uncloud image pins `ghcr.io/unlabs-dev/corrosion:2026.6.15`. ([image pin](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/corroservice/docker.go#L21-L25))
2. Keep every daemon as an equal entry point. Let the contacted daemon route commands from its local machine map. Do not introduce a leader, quorum, consensus-backed control plane, or globally serialized command bus.
3. Keep imperative Docker operations as direct calls to selected machines. Keep replicated state for observation and asynchronous DNS and Caddy projection. Do not turn stored container rows into desired state.
4. Keep availability partition-local. Accept local mutations during partitions. Return partial broadcast results and warnings where Uncloud does. Do not block minority-side administration.
5. Keep uniqueness and allocation optimistic. Local snapshot checks are validation, not global invariants. Do not add fencing, leases, reservations, or consensus allocation.
6. Keep operations non-transactional across containers and machines. Preserve the narrow replacement compensation path and otherwise expose partial success and retained artifacts.
7. Keep failure recovery local to Docker. Do not automatically move containers, rebalance replicas, or reconcile a desired replica count after failure.
8. Carry the architecture-significant TODOs into the corresponding Rust locations. This includes the absent machine-add consensus gate, absent membership filtering in DNS and Caddy, unused `sync_status` semantics, removal scheduling race, and asynchronous Caddy rollout gap. ([machine add TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/cluster/cluster.go#L174-L175), [DNS TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/dns/resolver.go#L38-L68), [Caddy TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/internal/machine/caddyconfig/controller.go#L132-L146), [removal TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/cmd/uc/machine/rm.go#L98-L100), [rollout TODO](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/pkg/client/deploy/operation/container.go#L240-L246))

Rust can make the weak model harder to misread with types rather than new protocols. Useful distinctions include `Live<T>` versus `Replicated<T>`, `Complete<T>` versus `Partial<T, MachineFailure>`, and explicit local membership states such as `Up`, `Suspect`, and `Down`. An allocation result should be named as a locally selected candidate, not a globally reserved subnet. These types document epistemic state. They must not claim stronger distributed guarantees than the Go behavior provides.

## Research boundary

This report characterizes the frozen baseline. It does not recommend consensus, fencing, reconciliation, or stronger transactional behavior. Those would change the product's architecture and increase implementation scope. The relevant design hypothesis is that Uncloud serves relatively small clusters with low churn, few conflicts, and fast-enough propagation. The reconstruction should retain that bet unless a later product decision explicitly changes it. ([design hypothesis](https://github.com/psviderski/uncloud/blob/b7e224a1eff98813b1d1a32034d977be24be994e/misc/design.md#L95-L97))
